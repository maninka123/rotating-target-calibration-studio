# Design decisions

This file records choices made where the specification allowed or required an implementation decision.

| Decision | Choice and rationale |
| --- | --- |
| Coordinate system | The target lies in the XY plane and sensor optical axes lie on +Z, looking toward the origin. This makes target-plane projection and the Three.js scene use the same convention. Positive target rotation is counter-clockwise in target coordinates. |
| Ray model | Every generated point begins as a double-precision ray direction and is intersected analytically with the target plane. Camera pixels are treated as individual rays in the target-region lattice; no render/read-back path is used. |
| Camera workload | Camera pixels are pinhole rays derived from resolution, pixel pitch and focal length. Only the square pixel crop enclosing the projected disc is evaluated; it includes disc misses near the circular edge and every ray that can enter estimation. |
| Camera span units | Samples across target converts focal length from millimetres and pixel pitch from micrometres into one consistent metre basis. This removes a display-only 1000× scale error while leaving analytic ray generation unchanged. |
| Sampling density | Working-band count is computed only by classifying generated scan rays. The schema contains no nominal band count, target-span fraction or ring-count calibration field. |
| Scan architectures | Heads enumerate channel elevation by azimuth, prisms sum two rotating wedge deflections, micro-mirrors combine a sinusoidal fast axis with a slow ramp, arrays enumerate a fixed angular grid, rotating mirrors combine emitters with mirror azimuth, and cameras enumerate pinhole pixels. |
| Prism visual fidelity | Prism deflections are normalised to each sensor's stated horizontal and vertical field of view. Higher counter-rotation rates produce dense multi-lobed coverage within a 100 ms frame while acquisition-dependent phases keep consecutive frames distinct. Rates are simulation parameters, not claimed internal motor specifications. |
| Avia centre coverage | The Avia prism pair uses closely matched deflection magnitudes so opposing prism vectors sweep through the full hub region. The previous larger mismatch imposed an artificial gap outside the hub; exact equality also made the ideal trajectory unrealistically singular at the optical axis. The sensor projection draws the red analysis-exclusion hub beneath samples, making those rays visible while continuing to exclude them from estimation. |
| Simulation control | The header contains one stateful, high-contrast Play/Pause control. Redundant simulation and real-time chips were removed; the scene view retains its compact real-time indicator where it has direct context. |
| Sweep feedback | Long sweeps show a compact target glyph rotated by completed fraction, exact percentage, completed/total acquisitions and a progress bar. The indicator exists only while work is active so completed results remain uncluttered. |
| Single-plane scanner | The one-dimensional scan is retained as an explicit architecture, but the geometric estimator rejects it before optimisation because it cannot constrain two-dimensional aperture boundaries. |
| Non-repeating prism phase | Acquisition index advances an irrational-like phase, ensuring successive prism acquisitions do not start at the same rosette point. |
| Sample timing | Moving scanners advance observation time with scan order. Global-shutter camera pixels share the exposure midpoint; rolling rows advance from the end of exposure through readout. Reported timestamp convention remains separate from those observation times. |
| Estimator comparison truth | Error is measured against target angle at the sensor-reported timestamp. A sequential acquisition therefore exposes the intended timestamp-to-mean-observation offset. |
| Contour matching | Sparse rings reject from inadequate boundary support. Prism frames model an intermediate correspondence stage: most select the correct feature association, while a deterministic minority select the 180° alternative. This produces low median error with visible gross outliers rather than silently rejecting wrong matches. |
| Boundary-fit optimizer | A user-adjustable coarse global sweep, defaulting to 1°, is followed by golden-section refinement. Binary disagreement is softened only inside a 1.25° clipped boundary margin. All working-band samples participate. |
| Density validation diagnosis | The old sparse/dense test changed array dimensions without changing pinhole pixel pitch, so the target crop contained the same physical ray lattice and both errors were 0.0336°. The revised test models downsampling by increasing effective pixel pitch and compares several angles; density now genuinely changes. This was not a search-resolution floor. |
| Micro-mirror rejection | The slow-axis ramp covers only part of its travel per acquisition. Acquisition phase therefore makes some frames miss adequate two-dimensional support naturally, producing a non-zero rejection rate without injecting a stored failure probability. |
| Local uncertainty | Curvature uses symmetric 0.05° finite differences. The UI explicitly warns that near-zero dense-grid values are numerical conditioning, not total repeatability. |
| Mechanical span | The supplied deflection validation value of 2.73 mm is only obtained with the unsupported radial span `R − hub radius = 160 mm`, not the full 210 mm outer radius stated beside the equation. The implementation uses the unsupported span and documents this specification inconsistency. |
| Custom sensors | User definitions are persisted only in `localStorage`; configuration JSON remains the portable interchange mechanism. |
| Display decimation | Canvases cap display at approximately 20,000 samples by stride. Typed-array frames passed to estimators are never decimated. |
| Renderer loading | The Three.js viewport is imported with React lazy loading, placing the renderer in a separate production chunk requested only when Panel 3 renders. |
| Worker lifecycle | The simulation worker is created lazily on first request and can be recreated after termination. This keeps local development functional when strict effect checks deliberately mount, clean up and remount effects. |
| 3D geometry refresh | The scene previously keyed its extruded mesh only to the target object reference and left resource cleanup implicit. The target mesh now derives an explicit signature from every geometric field, rebuilds from immutable state, and disposes all replaced geometries and materials. DOM test hooks remain outside the Three.js graph because hyphenated DOM attributes are interpreted there as nested object properties. |
| Rim-connected apertures | Annular sectors reach the outer rim, so representing them as closed polygon holes creates coincident boundaries and invalid triangulation. The target is extruded from one star-shaped notched contour assembled at every aperture boundary, including overlapping sectors, with no coincident hole paths. |
| Hub representation | The old axial cylinder was oriented perpendicular to the target face and appeared to be a second plate. All views now read the same target hub radius through shared conversion helpers; the 3D hub is a red, flush face marker with no added thickness. |
| Engineering annotations | Stand-off and background dimensions are native scene objects with double-arrow lines and camera-facing labels. They share live target and sensor state and can be disabled as a group. |
| Scene annotation scope | The main scene retains only sensor stand-off and background-plane distance labels. Target diameter, hub, thickness and aperture dimensions are grouped beside the editable target preview, where they remain readable without obscuring the 3D geometry. |
| Field-of-view display | Each active sensor has a colour-matched translucent frustum surface and outline. A shared visibility switch and low-range opacity slider prevent overlapping fields of view from dominating the scene. |
| Result grouping | Frozen-frame results are grouped once per sensor. A shared projection layers thick contour and geometric fits beneath a dashed ground-truth template, with estimator errors in one table, avoiding duplicate sample plots. |
| Rotation view | A lightweight orthographic SVG uses the same target geometry state, radius conversion and simulation angle as the main scene. Avoiding a second interactive WebGL event root makes this motion-only view simpler and more robust while retaining exact sector openings and crisp edges. |
| Styling | Native system fonts avoid network font requests. The sole accent is teal; material, aperture and background use the same muted palette in every 2D/3D view. |
| GitHub Pages base | Production Actions builds use `/rotating-target-calibration-studio/`; local builds use `/`. This supports both repository-subpath deployment and normal local preview. |
| Browser support | Current evergreen browsers with Web Workers, WebGL2, typed arrays, modules, `structuredClone`, and `crypto.randomUUID` are targeted. |
