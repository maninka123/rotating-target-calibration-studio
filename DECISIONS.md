# Design decisions

This file records choices made where the specification allowed or required an implementation decision.

| Decision | Choice and rationale |
| --- | --- |
| Coordinate system | The target lies in the XY plane and sensor optical axes lie on +Z, looking toward the origin. This makes target-plane projection and the Three.js scene use the same convention. Positive target rotation is counter-clockwise in target coordinates. |
| Ray model | Every generated point begins as a double-precision ray direction and is intersected analytically with the target plane. Camera pixels are treated as individual rays in the target-region lattice; no render/read-back path is used. |
| Camera workload | Camera pixels are pinhole rays derived from resolution, pixel pitch and focal length. Only the square crop enclosing the projected disc is evaluated; it includes every ray that can enter estimation. Full-frame row timing is computed independently of that crop. |
| Camera FOV defect | Camera definitions previously stored FOV beside optical parameters, allowing disagreement. FOV is now derived only as `2 atan(resolution × pitch/(2f))`, and camera builder controls expose resolution, pitch and focal length. Thermal optics give 54.5° × 44.8°. The stated FLIR optics generate 103,276 band pixels, so 87,264 was inconsistent with those parameters. |
| Camera span units | Samples across target converts focal length from millimetres and pixel pitch from micrometres into one consistent metre basis. This removes a display-only 1000× scale error while leaving analytic ray generation unchanged. |
| Sampling density | Working-band count is computed only by classifying generated scan rays. The schema contains no nominal band count, target-span fraction or ring-count calibration field. |
| Original ring-count defect | Channel elevations were enumerated correctly by the ring helper, but generated head rays used spherical elevation, making target-plane height grow as `d tan(θ)/cos(azimuth)`. The renderer also showed only a generic pyramid. Generated rings now keep `h = d tan(θ)` at every azimuth, and both the live count and visible channel surfaces use the same individually evaluated elevation list. |
| Rotating multi-channel heads | Channels are uniform and symmetric over vertical FOV; each channel is paired with every 360° azimuth step. Target intersections use fixed ring height, and chord samples arise from actual azimuth rays. The scene shows a full annular band plus one thin surface for every channel that crosses the target. |
| Prism visual fidelity | Prism deflections are normalised to each sensor's stated horizontal and vertical field of view. Higher counter-rotation rates produce dense multi-lobed coverage within a 100 ms frame while acquisition-dependent phases keep consecutive frames distinct. Rates are simulation parameters, not claimed internal motor specifications. |
| Prism mode | Avia is represented by a non-repetitive multi-line rosette mode, not as a single fixed beam line. Horizon and Tele-15 use the same two-wedge kinematic family with their own FOV and rates. Longer integration adds genuine trajectory samples and increases occupied coverage. The 3D envelope is elliptical rather than rectangular. |
| Oscillating micro-mirror | The reference Cube 1 model uses 70° × 30°, 200 scan lines and a 1 kHz mirror eigenfrequency. Frame duration is `lines/(2f)`. Horizontal angle is sinusoidal; vertical angle uses the same carrier at +π/4 phase with a 0→1→0 frame ramp, creating an eye rather than a filled rectangle. The 97 kHz pulse rate is a modelling parameter. Sparse custom pulse-rate modes demonstrate graceful rejection. |
| Solid-state array | Rays form a fixed rectangular angular grid from configured rows, columns and FOV. Consecutive frames therefore have identical positions. Its rectangular-pyramid coverage volume is exact for this ideal grid. |
| Rotating mirror and pitch | Mid-360 has its own 200,000 point/s, 10 Hz rotating-mirror path. Pitch is added to every native −7°/+52° ray elevation and to the rendered band. At zero pitch the lower target is clipped; −22.5° centres coverage. Applying the existing 10% safety margin consistently gives a 0.408 m centred minimum; 0.372 m is the corresponding un-margined distance. |
| Single-plane scanner | Rays step only in horizontal angle with zero elevation extent. The scene uses a flat fan, and the geometric estimator rejects the missing two-dimensional boundary coverage. |
| Cameras | Each evaluated pixel produces a pinhole ray from resolution, pixel pitch and focal length. Global pixels share exposure time; rolling rows advance in time. Camera coverage is the rectangular pyramid defined by the actual image bounds. |
| Avia centre coverage | The Avia prism pair uses closely matched deflection magnitudes so opposing prism vectors sweep through the full hub region. The previous larger mismatch imposed an artificial gap outside the hub; exact equality also made the ideal trajectory unrealistically singular at the optical axis. The sensor projection draws the red analysis-exclusion hub beneath samples, making those rays visible while continuing to exclude them from estimation. |
| Simulation control | The header contains one stateful, high-contrast Play/Pause control. Redundant simulation and real-time chips were removed; the scene view retains its compact real-time indicator where it has direct context. |
| Sweep feedback | Long sweeps show a compact target glyph rotated by completed fraction, exact percentage, completed/total acquisitions and a progress bar. The indicator exists only while work is active so completed results remain uncluttered. |
| Sweep review and runtime estimate | Sweep confirmation presents the current immutable run inputs and estimates wall time from generated ray count, acquisition count and estimator workload. It is labelled as approximate because browser and hardware throughput vary. |
| Sweep output | Where the File System Access API is available, the user chooses a parent location and the app creates a timestamped run folder with per-acquisition CSV, summary JSON and configuration JSON. Unsupported browsers receive one self-contained JSON package because ordinary web downloads cannot create directories. |
| Independent sweep execution | Live frames and frozen-frame estimation retain their worker while batch sweeps use a second worker. A long sweep therefore does not block the simulation clock or panels 1–5. |
| First-load notice | A localStorage flag suppresses the work-in-progress notice after dismissal. The header link reopens the same accessible dialog; keyboard focus is trapped while open and restored to that link on close. |
| Target designer layout | Presets, inputs, aperture rows and statistics share a content-sized left column. The preview and dimensional summary occupy the full-height right column, avoiding the empty row previously created when statistics spanned beneath the taller preview. |
| Non-repeating prism phase | Acquisition index advances an irrational-like phase, ensuring successive prism acquisitions do not start at the same rosette point. |
| Sample timing defects | Moving scanners advance observation time with scan order. Global pixels share exposure midpoint. Rolling rows now use row start plus half the exposure; the previous model incorrectly added a full common integration period before readout. Mean time averages only working-band samples. Reported instants are first observation, frame/window start, sample-span midpoint, and first-row exposure start respectively. The two start conventions can coincide. |
| Estimator comparison truth | Error is measured against target angle at the sensor-reported timestamp. A sequential acquisition therefore exposes the intended timestamp-to-mean-observation offset. |
| Contour truth leak | The old prism branch read target truth, injected a 180° result from acquisition index and otherwise fell back to the geometric estimator. Both estimators now accept only classified target-plane arrays, observation times, target geometry and settings. Truth is supplied only to a separate evaluation function. Contour matching extracts class-supported aperture boundaries into inner/outer polygon chains, matches measured width and inner radius, and rejects unsupported or inconsistent correspondence; it never calls the geometric fit. |
| Honest contour profile | A corrected 300-frame Avia sweep accepts 217 frames, rejects 27.7%, and yields 1.341° MAE and 1.275° median absolute error. It has no manufactured near-180° outliers, and no statistical failure profile is asserted. |
| Sweep rotation defect | Sweep start time previously cancelled inside relative-time rotation while every initial angle was zero, so all acquisitions began at one orientation. Acquisition `i` now starts at `360 × rotations × i/N`; a circular-gap regression test verifies coverage. Earlier sweep results were discarded. |
| Circular comparisons | Estimate errors, pairwise error differences and symmetry comparisons use signed circular wrapping. Golden refinement may bracket across 0°/360° because its objective wraps every trial. Pairwise timing output reports each sensor pair independently. |
| Symmetry and overlap | Exact twofold and threefold target symmetries are detected and comparable global minima reject as `orientation ambiguous` with order. Editable and imported targets reject overlapping aperture sectors, preventing double-counted area, sensitivity and moments. Imported widths are capped at 179°. |
| Boundary-fit optimizer | A user-adjustable coarse global sweep, defaulting to 1°, is followed by golden-section refinement. Binary disagreement is softened only inside a 1.25° clipped boundary margin. All working-band samples participate. |
| Density validation diagnosis | The old sparse/dense test changed array dimensions without changing pinhole pixel pitch, so the target crop contained the same physical ray lattice and both errors were 0.0336°. The revised test models downsampling by increasing effective pixel pitch and compares several angles; density now genuinely changes. This was not a search-resolution floor. |
| Micro-mirror rejection | The 97 kHz reference pattern is well supported in the ideal scene. A sparse 5 kHz mode rejects 5 of 300 acquisitions from inadequate natural support, demonstrating the architecture's failure mode without a stored failure probability. |
| Local curvature proxy | Curvature uses symmetric finite differences tied to search resolution. It is a numerical sharpness proxy, not a statistically justified uncertainty. |
| Mechanical span | The supplied deflection validation value of 2.73 mm is only obtained with the unsupported radial span `R − hub radius = 160 mm`, not the full 210 mm outer radius stated beside the equation. The implementation uses the unsupported span and documents this specification inconsistency. |
| Custom sensors | User definitions are persisted only in `localStorage`; configuration JSON remains the portable interchange mechanism. |
| Display decimation | Canvases cap display at approximately 20,000 samples by stride. Typed-array frames passed to estimators are never decimated. |
| Renderer loading | The Three.js viewport is imported with React lazy loading, placing the renderer in a separate production chunk requested only when Panel 3 renders. |
| Worker lifecycle | The simulation worker is created lazily on first request and can be recreated after termination. This keeps local development functional when strict effect checks deliberately mount, clean up and remount effects. |
| Worker failure handling | A worker error rejects all pending requests, clears the queue and terminates the failed worker so it can be recreated instead of leaving callers hanging. |
| Rotation continuity | One application clock owns base angle and time origin. Play/pause, RPM and manual orientation reset it; both target views consume the same angle and no renderer integrates a private counter. |
| Numeric entry | Number fields retain their raw edit string. Empty, non-finite and out-of-range values show an inline error and are not committed to simulation state. |
| Configuration import | Imported JSON is validated field by field, including target dimensions, aperture overlap, RPM, search resolution, optics, FOV, timing, rates, pitch and architecture-specific parameters. Errors identify the invalid field. |
| Cross-sensor assumption | Relative observation-time recovery assumes constant angular speed over the sweep. |
| Sweep review controls | Acquisition count is interpreted per revolution. The review dialog can select 0–20 RPM and 1–20 revolutions without changing the live configuration. Runtime estimation includes ray count, total acquisitions and global-search steps; optional progress detail reports current rotation, acquisition and RPM. |
| 3D geometry refresh | The scene previously keyed its extruded mesh only to the target object reference and left resource cleanup implicit. The target mesh now derives an explicit signature from every geometric field, rebuilds from immutable state, and disposes all replaced geometries and materials. DOM test hooks remain outside the Three.js graph because hyphenated DOM attributes are interpreted there as nested object properties. |
| Rim-connected apertures | Annular sectors reach the outer rim, so representing them as closed polygon holes creates coincident boundaries and invalid triangulation. The target is extruded from one star-shaped notched contour assembled at every aperture boundary, including overlapping sectors, with no coincident hole paths. |
| Hub representation | The old axial cylinder was oriented perpendicular to the target face and appeared to be a second plate. All views now read the same target hub radius through shared conversion helpers; the 3D hub is a red, flush face marker with no added thickness. |
| Engineering annotations | Stand-off and background dimensions are native scene objects with double-arrow lines and camera-facing labels. They share live target and sensor state and can be disabled as a group. |
| Scene annotation scope | The main scene retains only sensor stand-off and background-plane distance labels. Target diameter, hub, thickness and aperture dimensions are grouped beside the editable target preview, where they remain readable without obscuring the 3D geometry. |
| Field-of-view display | Coverage is architecture-specific: annular bands for rotating heads and mirrors, elliptical cones for prisms, a faint rectangular envelope for the sparse micro-mirror, a flat fan for the single-plane scanner, and rectangular pyramids for arrays and cameras. All stop just past the target plane and share the existing opacity control. |
| Result grouping | Frozen-frame results are grouped once per sensor. A shared projection layers thick contour and geometric fits beneath a dashed ground-truth template, with estimator errors in one table, avoiding duplicate sample plots. |
| Rotation view | A lightweight orthographic SVG uses the same target geometry state, radius conversion and simulation angle as the main scene. Avoiding a second interactive WebGL event root makes this motion-only view simpler and more robust while retaining exact sector openings and crisp edges. |
| Styling | Native system fonts avoid network font requests. The sole accent is teal; material, aperture and background use the same muted palette in every 2D/3D view. |
| GitHub Pages base | Production Actions builds use `/rotating-target-calibration-studio/`; local builds use `/`. This supports both repository-subpath deployment and normal local preview. |
| Browser support | Current evergreen browsers with Web Workers, WebGL2, typed arrays, modules, `structuredClone`, and `crypto.randomUUID` are targeted. |
